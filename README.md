# bruce-graphql

Bruce's GraphQL CodeGen generates typed Rust from a GraphQL schema and a set of queries. An application's build script
gives the builder the schema and the queries the application makes, and the builder writes Rust types for each query's
variables and response. The application then makes its requests through the runtime library.

| Crate                        | What it is                                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `bruce-graphql`              | The runtime: requests, authenticated requests, errors, and the types the generated code uses, e.g. pages and edges. |
| `bruce-graphql-builder`      | The code generator, used from a build script.                                                                       |
| `bruce-graphql-builder-test` | Tests and examples of the builder, not published.                                                                   |

Its first user is [Bruce's Smart Home](https://github.com/bruceskingle/bruce-smart-home), a desktop app for seeing a
household's energy, which uses it for Octopus Energy's API. It was called `sparko_graphql` before 0.5.0.

# Why another GraphQL crate

When I started Bruce's Smart Home I needed a GraphQL client. I looked at the existing crates, and decided to write my
own, for two reasons.

## Generated code you can read

Code generated by a procedural macro cannot be seen in an IDE. That suits derives such as `Debug` and `Clone`, whose
code is obvious and never needs reading, but mapping a GraphQL API onto Rust types involves many details, and I wanted
to be able to click through a call into the generated code and see exactly what it does.

So bruce-graphql generates its code in a build script, as an ordinary Rust file in Cargo's build directory under
`target/`, which the application includes with `include!`. The IDE indexes it like any other source file, so the
generated types can be browsed, searched and stepped through.

The schema and the queries are kept as plain `.graphql` files in the application's repository, e.g. under `graphql/`:

```
graphql/octopus/
├── octopus-schema.graphql   the API's schema, fetched with fetch-schema.sh
├── account.graphql
├── bill.graphql
├── meter.graphql
└── ...
```

Keeping them as files means they are written and reviewed as GraphQL, with a GraphQL editor's highlighting and
checking, and can be tried out against the API in any GraphQL tool before any Rust is written; a change to the schema,
fetched again, shows up as a diff. The build script names them:

```rust
// build.rs
fn main() -> Result<(), Box<dyn std::error::Error>> {
    bruce_graphql_builder::builder("graphql")
        // GraphQL scalars and the Rust types they become.
        .with_type("Date", "bruce_graphql::types::Date")
        .with_type("DateTime", "bruce_graphql::types::DateTime")
        .with_schema("graphql/octopus/octopus-schema.graphql")
        // Each query file, and the module its types are generated in.
        .with_query("graphql/octopus/account.graphql", "account")
        .with_query("graphql/octopus/meter.graphql", "meter")
        .build()?;
    Ok(())
}
```

The builder writes `graphql.rs`, named by `builder("graphql")`, into the build script's `OUT_DIR`, with a module for
each query file and, within it, one for each query. The application includes it where it wants the types to live:

```rust
// src/octopus.rs
include!(concat!(env!("OUT_DIR"), "/graphql.rs"));
```

If the queries do not match the schema, the builder lists the errors in the generated file, where the IDE shows them,
and adds a `compile_error!`, so that the build fails rather than running with types that do not match the API.

For example, this query, from Bruce's Smart Home's `meter.graphql`:

```graphql
query accountPropertiesMeters($accountNumber: String!) @bruce_required_by_default {
  account(accountNumber: $accountNumber) {
    properties {
      id
      address
      postcode
      occupancyPeriods {
        id
        effectiveFrom
        effectiveTo @bruce_optional
        isOccupier
      }
      coordinates {
        latitude
        longitude
      }
      ...
```

generates, among others, these types, in the module `graphql::meter::account_properties_meters`:

```rust
#[derive(Serialize, Deserialize, Debug, DisplayAsJsonPretty, Clone)]
pub struct OccupancyPeriodType {
    #[serde(rename = "id")]
    pub id_: String,
    #[serde(rename = "effectiveFrom")]
    pub effective_from_: DateTime,
    #[serde(rename = "effectiveTo")]
    pub effective_to_: Option<DateTime>,
    #[serde(rename = "isOccupier")]
    pub is_occupier_: bool,
}

#[derive(Serialize, Deserialize, Debug, DisplayAsJsonPretty, Clone)]
pub struct PropertyType {
    #[serde(rename = "id")]
    pub id_: String,
    #[serde(rename = "address")]
    pub address_: String,
    #[serde(rename = "postcode")]
    pub postcode_: String,
    #[serde(rename = "occupancyPeriods")]
    #[serde(default, deserialize_with = "bruce_graphql::types::list_without_nulls")]
    pub occupancy_periods_: Vec<OccupancyPeriodType>,
    #[serde(rename = "coordinates")]
    pub coordinates_: CoordinatesType,
    ...
}
```

and a `Query` with a builder for its variables, which the application makes the request with:

```rust
let query = meter::account_properties_meters::Query::builder()
    .with_account_number(account_number.clone())
    .build()?;
```

## Fewer `Option`s

The second reason was nullability. In GraphQL a field is nullable unless it is declared otherwise, and many schemas
leave fields nullable even where a value is always expected. A list declared simply in GraphQL is nullable, and so is
each of its items, so that a generator following the schema exactly produces `Option<Vec<Option<SomeType>>>`.

The JSON values `null`, `[]`, `[null]` and `[null, null]` are all valid and distinct, but an API which gave them
different meanings would be unusual, and Rust code which has to handle every one of them is hard to read. A dynamically
typed language can ignore the question, until a null arrives where none was expected.

bruce-graphql therefore generates every list as a `Vec` of required items. A list which is null is read as an empty
list, and nulls within a list are left out, with a message saying so (`bruce_graphql::types::list_without_nulls`).

Other fields follow the schema: a field which the schema allows to be null is an `Option`. Directives in a query can
override that, treating fields as required which the schema says are nullable. Use them with care. I have been caught
out by fields which "could never be null" being returned as null months after they were first published with values,
at which point the code fails to read the response. Unless you are certain a field will always have a value, leave it
as an `Option` and handle `None`.

## Directives

The builder recognises these directives in query files. Any other directive is reported as a warning.

| Directive                    | Where                                    | Effect                                                                                                                                                                                                             |
| ---------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `@bruce_required_by_default` | A query, mutation, fragment or a field   | Every field selected within it is treated as required, as if the schema declared it non-null, so that its type is not an `Option`, unless the field has `@bruce_optional`. On a field, it applies to the fields selected within that field. |
| `@bruce_optional`            | A field                                  | The field follows the schema, an `Option` if the schema allows it to be null, within a selection that is required by default.                                                                                    |
| `@bruce_required`            | A field                                  | The field alone is treated as required, whatever the schema says.                                                                                                                                                 |
| `@bruce_currency`            | A field of type `String`                 | The field is read as an ISO 4217 currency code, as a `bruce_graphql::types::Currency`, rather than a `String`. On a field of any other type it is an error.                                                     |

A response which has null in a field treated as required fails to deserialize, and the request returns an error.
